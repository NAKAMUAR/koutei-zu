# チャット連携（外部AIエージェント）設計

作成: 2026-07-27 / 版: 3.1 / 状態: **設計のみ（未実装）**

Telegram + Cloudflare Worker + Gemini の自作エージェントと、工程図アプリをつなぐ設計。

```
① チャット（案件登録 / 状況確認）
      ↓
② 工程図（データの書き込み / 読み取り）
      ↓
③ 結果をチャットへ返答
```

**利用者はオーナー本人のみ**を前提とする。

- **第1部**：概要（非エンジニア向け）— 何ができて何ができないか
- **第2部**：技術仕様（実装者向け）

# 第1部　概要（非エンジニア向け）

## 0. 登場人物

やりたいことに関わる「部品」は6つあります。

| 名前 | 役割をひとことで |
|---|---|
| **Telegram** | スマホのチャットアプリ。**入口** |
| **Cloudflare Worker** | ネット上に置いた小さな自動処理プログラム。**受付係**。今回の主役 |
| **Gemini** | 文章の意味を読み取るAI。「A棟 外観1 白8時間」を項目に分解する係。**実は必須ではありません**（→ 第6章） |
| **Firestore（Firebase）** | 工程図のデータが実際に入っている**金庫**。案件・視点・ステップが全部ここ |
| **工程図アプリ** | ブラウザで開く画面。金庫の中身を見せたり書き換えたりする |
| GitHub / Vercel | 今のBotがWebページを公開している先。**今回の連携では使いません** |

ポイントは、**工程図アプリと Bot は「同じ金庫（Firestore）」を共有できる**ということです。
Bot がアプリを操作するのではなく、Bot が直接金庫を開けます。だからアプリを開いていなくても動きます。

---

## 1. 現状の工程

チャットにメッセージを送ってから返事が来るまでを、8ステップに分けます。
**✅ = すでに動いている / 🔧 = 今あるものに手を入れる / ❌ = これから新規に作る**

| # | 工程 | 状態 |
|---|---|---|
| **1** | スマホの Telegram にメッセージを送る | ✅ できている |
| **2** | Telegram がインターネット経由で Cloudflare Worker に届ける | ✅ できている |
| **3** | Worker が「送信者は本人か」を確認する（他人からの指示を無視する） | ✅ できている |
| **4** | 文章を読み取って「登録したいのか／状況を知りたいのか」を判断する | 🔧 仕組みはある。工程図用の作り込みが必要（**コマンド式ならAI不要** → 第6章） |
| **5** | Worker が**工程図の金庫（Firestore）にログインする** | ❌ **これから**。ここが最初の関門 |
| **6** | 金庫を**読む**（状況確認）／**書く**（案件登録） | ❌ **これから**。本体 |
| **7** | 結果を日本語の文章にまとめる | ✅ できている |
| **8** | Telegram に返信する | ✅ できている |

### 読み解き

**新しく作るのは 5 と 6 だけ**です。1〜4 と 7〜8 は、今のBotがすでに持っている仕組みをそのまま使えます。
今のBotは「6の代わりにWebページを作ってVercelに公開していた」だけなので、その部分を「工程図の金庫を読み書きする」に差し替えるイメージです。

### 参考：今の案件登録の工程（アプリでの手作業）

| # | 工程 |
|---|---|
| 1 | PCで工程図アプリを開く |
| 2 | 「案件」タブのフォームに、会社・案件名・視点・ステップ・時間・担当者・納期を入力 |
| 3 | 保存 → 金庫（Firestore）に書き込まれる |
| 4 | アプリが稼働時間・休日から**予定を計算し直して**、カレンダーや担当者別に反映 |

**4の「予定の計算」がアプリの中にしか無い**という点が、後で効いてきます（→ 第4章）。

## 2. 実現可能な事

### 2-1. 状況確認（読み取り）　★難易度：低・リスクほぼゼロ

チャットで質問すると、工程図の中身を答えてくれます。

- 「今どんな案件がある？」→ 会社別の案件一覧
- 「A棟の進捗は？」→ 各ステップの完了時間 / 全体時間（例：12時間中4時間完了）
- 「今週納期の案件は？」→ 納期が近い順
- 「ヤマダの残り作業は？」→ 担当者ごとの残り時間の合計
- 「今、確認待ちの案件は？」→ 確認待ち一覧

**これが一番おすすめです。** 読むだけなのでデータを壊しようがなく、外出先で「今どうなってる？」が分かるという、一番使う場面をカバーします。

### 2-2. 案件登録（書き込み）　★難易度：中

```
あなた: /案件 TAMAZEN A棟 外観1 白8h 色付4h 担当ヤマダ 納期8/5

Bot:  【この内容で登録しますか？】
      会社：TAMAZEN　案件：A棟
      納期：2026-08-05
      ─ EX1（担当：ヤマダ）
         白色  8:00
         色付  4:00
      合計 12:00
      　[ 登録する ]　[ やめる ]

あなた: [登録する] をタップ

Bot:  登録しました。PCの工程図にも反映されています。
```

技術的な調査の結果、**Bot が正確に作らないといけないのは実質3つだけ**と分かりました。残りはアプリ側が読み込み時に自動で整えてくれます（優先順位の番号など）。

1. 同じ案件の中で、会社名・案件名の文字を完全に揃える（1文字違うと別案件に分裂します）
2. 作業時間を分単位で入れる（8時間 → 480）
3. ステップの種類（白色・色付など）をマスタのIDで指定する ← ここを外すと請求・売上の集計が狂います

### 2-3. 取り消し

`/取消` で直前に登録した案件を丸ごと削除できます。登録時に目印を付けておくので確実に消せます。

### 2-4. PCへの即時反映

工程図アプリは金庫の変化をリアルタイムで見張っています。**PCでアプリを開いていれば、スマホから登録した案件が数秒で画面に出ます。**

### 2-5. 画像から登録

今のBotにある「画像を送るとGeminiが読み取ってCSVにする」機能を、そのまま登録に流用できます（工程表のスクショを送って登録、など）。ただし読み間違いが増えるので、2-2の確認は必須です。

## 3. 確認が必要な事

**着手前に決めていただきたいこと**を、重要度順に5つ。

### 3-1. ★最重要：AIを使うかどうか（使うなら案件情報が外部サーバーを通ります）

自由文をAIに解釈させる場合、**会社名・案件名・担当者名が Google のサーバーに送られます**。
「TAMAZENのA棟を8月5日納期で」という情報が外部に出るということです。

これは技術的な問題ではなく**業務上の判断**です。お客様との守秘義務契約がある場合は特に確認が必要です。

→ **ただし、第6章のとおり AI は必須ではありません。** コマンド式・ボタン式にすれば、登録も確認もAIを一切通さずに実現でき、**この判断そのものが不要になります。**

### 3-2. Bot専用のGoogleアカウントを作る必要がある

工程図の金庫は今、「**メール確認済みの、許可リストに載っているアドレス**」しか開けない設定です（`firestore.rules`）。Botにも1つアカウントが要ります。

作業は次の4つ。**「確認メールを1回開く」を忘れると動きません**（一番よくある詰まりどころです）。

1. Bot用のGoogleアカウントを作る（例：`koutei-bot@gmail.com`）
2. Firebaseの管理画面で、そのアドレスをメール＋パスワードで登録する
3. **確認メールを開いて認証を完了させる**
4. 工程図アプリの「メンバー管理」から、そのアドレスを追加する

### 3-3. パスワードを Cloudflare に預けること

Botのパスワードは Cloudflare の「シークレット」という保管機能に入れます（今 `GITHUB_TOKEN` などを入れているのと同じ場所）。**GitHubには絶対に入れません。**
すでに同種の運用をされているので新たに増えるリスクは小さいですが、一応の確認です。

### 3-4. 「いつ終わる？」にどこまで答えてほしいか

これが第4章の制約に直結します。
「案件一覧と進捗が分かれば十分」なのか、「終了予定日まで答えてほしい」のかで、作る量が変わります。

### 3-5. スプレッドシート同期を今も使っているか

`sync/Code.gs`（スプレッドシート → 工程図の自動同期）は、**現在の設定では機能していないはず**です（旧仕様のまま。`docs/06` 第11項で既出）。
使っていないなら、この機会に退役させて経路を1本にした方が事故が減ります。

## 4. 実現不可能な事

**できないこと、および「今の作りのままでは無理なこと」**を正直に6つ。

### 4-1. アプリを一度も開かずに「A棟はいつ終わる？」に正確に答える　❌

**理由：終了予定日はどこにも保存されていないからです。**

工程図の「いつ始まっていつ終わる」は、金庫に入っているデータではありません。アプリが**画面を開くたびに、稼働時間・休日・お休み・案件の並び順から、その場で計算している**ものです（`src/lib/schedule.js`、約900行）。Botはこの計算機を持っていません。

金庫を読んで分かるのは「作業時間12時間・納期8/5・進捗4時間」までで、「7/30の15時に終わる」は出てきません。

→ **改善案①でほぼ解決できます**（「アプリが最後に計算した結果」を答える方式）。ただし「アプリを一度も開いていない状態で、常に正確」は原理的に無理です。

### 4-2. Botで登録した案件の「予定」が、その場で計算される　❌

上と同じ理由です。登録自体は成功しますが、**予定表への反映（何日の何時に作業するか）は、次にアプリを開いたときに計算されます。**
返答に「予定の再計算はアプリを開いたときに行われます」と添えるのが誠実です。

### 4-3. チャットだけで工程図の全機能を操作する　❌

請求書・見積書の作成、ドラッグでの案件並べ替え、カレンダー上での調整——**画面で見ながら判断する操作はチャットに向きません。**
チャットは「登録」と「確認」に絞り、それ以外はPCで、という住み分けが現実的です。

### 4-4. 確認なしの全自動登録を、安全に行う　❌

AIを使う場合、読み違いは必ず起きます（「8h」を8分と読む、似た会社名を取り違える等）。
工程図のデータは**請求・売上に直結**するため、確認ステップは外せません。「AIが自信を持っている時だけ自動」も、その自信の判定自体がAIなので保証にはなりません。

なお**コマンド式・ボタン式（第6章）なら読み違いは起きません**が、それでも打ち間違い・選び間違いはあるため、確認画面は残すことをおすすめします。

### 4-5. Vercelの公開ページに工程図のデータを載せる　❌

今のBotが作るWebページは、**URLを知っていれば誰でも見られます**（引き継ぎメモの「セキュリティ上の課題」に記載のとおり）。
お客様名・案件名を載せるのは避けてください。工程図の情報は**チャットの返信本文で返す**のが安全です。

### 4-6. 既存のスプレッドシート同期の仕組みを流用する　❌

匿名ログインで旧い保存場所に書く作りなので、現在のセキュリティ設定・データ構造では通りません。参考にはできますが、作り直しになります。

## 5. 改善案

### 改善案①　予定は「アプリが計算した結果を置いておく」方式にする　★推奨

4-1の解決策です。

**やること**：工程図アプリが予定を計算したとき、その要約を金庫に1枚だけ置いておく。Botはそれを読んで答える。

```
PCでアプリを開いている
    ↓ （計算のたびに、そっと1枚だけ保存）
金庫に「予定メモ」1枚
    ↓
Bot がそれを読んで「A棟は7/30 15時に終わる予定です（本日10:32時点）」
```

- **メリット**：アプリ側の追加は50行程度と小さい。Botは1枚読むだけ
- **デメリット**：アプリを閉じている間は情報が古くなる → **「（10:32時点）」と必ず添える**ことで誠実に運用できます

もう一つ「計算機ごとBotに積む」案もありますが、アプリ側を直すたびにBot側も貼り直しが必要で、**忘れると間違った予定を自信満々に答える**ようになります。おすすめしません。

---

### 改善案②　状況確認はAIを使わない　★強く推奨

**3-1（情報が外部に出る）・費用・回数制限の3つが同時に解決します。**

質問を自由文で受けるからAIが要るのであって、**コマンドを決めてしまえばAIは不要**です。

| コマンド | 返すもの | AI |
|---|---|---|
| `/状況` | 案件一覧と進捗 | 不要 |
| `/状況 A棟` | 特定案件の詳細 | 不要 |
| `/今日` | 今日の予定 | 不要 |
| `/納期` | 納期が近い順 | 不要 |
| `/担当 ヤマダ` | 担当者の残り作業 | 不要 |
| `/案件 〜`（登録） | — | **必要**（文章の解釈） |

文章の整形は決まった型（テンプレート）に流し込むだけで十分です。

**効果**
- **状況確認では案件情報が一切外部に出ません**（金庫 → Worker → Telegram だけ）
- 引き継ぎメモにあった「Gemini利用回数200回の警告」を、確認では消費しません
- 返答が速く、毎回同じ体裁になります

自由文（「A棟どうなってる？」）にも対応したければ、後から足せます。

---

### 改善案③　確認は「ボタン」で

`/確認` と打たせるのではなく、**メッセージに [登録する] [やめる] のボタンを付けます**（Telegramの標準機能。LINEにも同等の機能があります）。

歩きながら片手で操作するとき、打ち間違いによる誤登録を防げます。実装は数行です。

---

### 改善案④　読み取り専用から始める　★推奨

**書き込みは後回しにしてください。**

| 段階 | 内容 | 価値 |
|---|---|---|
| **第1段階** | 金庫にログインできるかだけ確認（マスタを1件読んで返す） | 詰まりどころ（3-2のメール確認など）を最初に全部潰せる |
| **第2段階** | `/状況` `/納期` `/担当` — **読むだけ** | **ここで実用になります。**外出先で状況が分かる。壊れる余地がゼロ |
| **第3段階** | 予定メモ（改善案①）を追加 → `/今日` `/状況 A棟` | 「いつ終わる」に答えられる |
| **第4段階** | `/案件` 登録・`/取消` | 双方向の完成 |
| **第5段階** | 画像からの登録 | 拡張 |

第2段階までなら本番データに一切書き込みません。**まずここまでを作って、実際に1〜2週間使ってみてから**、登録まで進めるか判断するのが安全で、しかも一番早く価値が出ます。

### 改善案⑤　チャットアプリはどれがよいか

ご要望の「Telegram以外が良い等」への回答です。結論から言うと——

> **今回は Telegram のまま進めることをおすすめします。**

| 候補 | 良い点 | 気になる点 | 評価 |
|---|---|---|---|
| **Telegram（現状）** | **すでに動いている**（工程1〜4・7〜8が資産として使える）。Bot機能が無料・無制限で、制約が一番少ない | 日本では利用者が少ない。お客様とのやり取りには使えない | **◎ 今回はこれ** |
| **LINE** | 日本の業務で圧倒的に使い慣れている。**将来スタッフにも使わせる場合は最有力**。返信は無料枠の対象外なので、コマンド→返信の使い方なら実質無料（※料金体系は変わることがあるので導入時に要確認） | Bot（LINE公式アカウント）の作成・つなぎ込みで作り直しが発生 | ○ 将来の乗り換え先 |
| **Slack** | 表や整形が一番きれい。PC・スマホ両対応で、過去のやり取りを検索しやすい | 普段使っていないなら、そのために開くのが面倒 | △ 社内で使っていれば有力 |
| **Discord** | Slackとほぼ同じ利点で完全無料 | 業務ツールとしては馴染みが薄い | △ |

**判断の理由**：利用者がご本人だけである以上、「みんなが使い慣れているか」は効いてきません。それより**すでに動いているものを活かせる**ことの方が価値が大きいです。

**乗り換えを検討すべきタイミング**は、次のいずれかが起きたときです。

- 社内の他のスタッフにも使わせたくなった → **LINE**
- お客様からの連絡をそのまま案件登録に流したくなった → **LINE**
- 表形式でしっかり見たくなった → **Slack**

なお、**今回の設計（第2部）はチャットアプリに依存していません。** 工程5〜6（金庫の読み書き）はどのアプリでも共通で、入口を差し替えるだけです。あとから乗り換えても、作ったものの大半は無駄になりません。

---

### 改善案⑥　工程図アプリ自体をスマホ対応させる（別軸の提案）

チャット連携とは別の選択肢として挙げておきます。

コードを確認したところ、**工程図アプリには画面幅に応じたレイアウト調整が1か所も入っていません**（レスポンシブ対応のコードがゼロ）。つまり現状は**完全にPC専用**です。「スマホだけで使えるように」という当初の動機は、ここから来ているはずです。

- **アプリをスマホ対応させる** → 全機能がスマホで使えるようになるが、画面数が多く**改修は大規模**になる
- **チャット連携** → 使える機能は「登録」と「確認」に限られるが、**小さく始められて、しかも速い**

「駅で3秒で状況を見たい」という用途では、アプリを開いてログインして読み込みを待つより、**チャットの方が確実に速い**です。両者は競合しません。

**おすすめは、まずチャット連携（改善案④の第2段階まで）**。それで足りない部分がはっきりしてから、アプリのスマホ対応に投資するか決めるのが無駄がありません。

## 6. AIは必要か（コマンド方式の検討）

### 6-1. 結論：AIは無くても作れます

**登録も確認も、決まった書式の命令文だけで実現できます。** AIは「自由に文章を書きたい」ための便利機能であって、必須ではありません。

| 機能 | AIなしで可能か | 補足 |
|---|---|---|
| 状況確認（`/状況` `/納期` `/担当` `/今日`） | ✅ **完全に可能** | 決まった書式で十分 |
| 案件登録（コマンド1行） | ✅ **可能** | 書式を覚える必要あり |
| 案件登録（ボタン対話式） | ✅ **可能・おすすめ** | 覚える必要すらない |
| 表記ゆれの吸収（たまぜん → TAMAZEN） | ✅ 可能 | `kanaNormalize`（全角半角・カタカナ→ひらがな変換）が**すでにアプリ内にあります** |
| 時間の解釈（`8h` / `8:00` / `8`） | ✅ 可能 | `parseHM` が**すでにアプリ内にあります** |
| 自由文（「A棟どうなってる？」） | ❌ AIが要る | コマンドで代替できます |
| **画像（工程表のスクショ）から登録** | ❌ **AIが要る** | ここだけは代替不可 |

上2つの変換処理は、アプリで使っているものをそのままBotにコピーできます（各15行程度）。

### 6-2. 「SQLのような命令文」について

3点に分けてお答えします。

**① SQLそのものは使えません**
工程図のデータが入っている Firestore は、SQLデータベースではありません（NoSQLと呼ばれる別の種類）。`INSERT INTO ...` のようなSQL文を受け付ける口がそもそも無いので、SQLを直接送ることはできません。

**② ただし「SQLのような、決まった書式の命令文」を自分で決めるのは完全に可能です。むしろ推奨します**
Bot側で「この書式で来たらこう解釈する」と決めておくだけです。文字列を区切って読むだけなので、AIは要りません。

**③ 読み取りの絞り込みには、SQLに似た仕組みがあります**
Firestore には「構造化クエリ」という機能があり、「未完了のものだけ」「この会社のものだけ」といった絞り込みができます（SQLの `WHERE` に相当）。これは Worker の内部で使うもので、こちらが書式を覚える必要はありません。

### 6-3. 命令文の具体案

#### 案A：1行式

```
/案件 会社=TAMAZEN 案件=A棟 視点=EX1 担当=ヤマダ 白=8h 色=4h 納期=8/5
```

- スペースと `=` で区切って読むだけ。**AI不要**、実装は数十行
- 短縮形も可： `/案件 TAMAZEN|A棟|EX1|ヤマダ|白8h,色4h|8/5`
- **弱点**：書式を覚える必要がある。打ち間違えるとエラーになる
- **対策**：`/ヘルプ` に例を載せる／エラー時に正しい例を返す／`/前回` で直前の登録を雛形として呼び出す

#### 案B：ボタン対話式　★おすすめ

```
/案件
  → 会社は？        [TAMAZEN] [SUMUS] [その他…]
  → 案件名は？       （入力）
  → 視点は？        [EX1] [EX2] [IN1] [その他…]
  → 担当は？        [ヤマダ] [タナカ] …
  → 白色の時間は？   [4h] [6h] [8h] [直接入力]
  → ステップ追加？   [色付] [終了]
  → 納期は？        [今週末] [来週末] [日付入力]
  → 【確認】…       [登録する] [やめる]
```

ボタンの選択肢は**工程図のマスタから自動生成**します。これが効きます。

- 書式を覚える必要がない
- 打ち間違いが起きない
- **選んだ値はマスタと必ず一致する** → 第2章で挙げた「Botが正確に作るべき3点」のうち2点（会社名・担当者名の一致、ステップ種類のID）が**構造的に保証されます**

スマホでは、打つよりタップの方が速く確実です。**これもAIは一切使いません。**

### 6-4. AIあり／なしの比較

| | **AIなし**（コマンド・ボタン） | **AIあり**（自由文） |
|---|---|---|
| 入力 | 書式に従う／タップ | 好きに書ける |
| 読み違い | **起きない** | 起きる（`8h` を8分と読む等） |
| 情報の外部送信 | **無し** | 会社名・案件名がGoogleへ |
| 費用・回数制限 | **無し** | Gemini の呼び出し回数を消費 |
| 応答速度 | 即座（1秒未満） | 1〜3秒 |
| 結果の再現性 | **毎回同じ** | 揺れることがある |
| 実装 | 単純。おかしくなっても原因を追える | プロンプトの調整が要る |
| 弱点 | 想定外の書き方に対応できない | 上記すべて |

### 6-5. おすすめの構成

**第1〜4段階（登録まで含めて）をAI完全なしで作れます。** その場合：

- **Gemini API キーが不要** → 引き継ぎメモにあった「200回制限」の心配が消える
- **確認事項 3-1（案件情報が外部に出る）が丸ごと無くなる** → 業務判断そのものが不要になる
- 動作が速く、結果が毎回同じで、不具合の原因を追いやすい

AIを足すのは、**第5段階（画像からの登録）**か、自由文に対応したくなったときだけで十分です。

> 補足：今のBotが持っている他の機能（Webページ生成など）でGeminiを使っている部分は、そのままで構いません。**工程図連携の部分だけAI不要**という話です。

## 10. 書き込み（案件登録）

### 10.1 Worker から直接書いてよい理由

不変条件の大半は**アプリの読み込み時に自己修復される**：

| 不変条件 | 実態 |
|---|---|
| `priority` の会社別 1..n 採番 | `normalizePriorities()` が**購読のたび**に全件を振り直す。Bot は `priority: 99`（末尾）でよい |
| 欠けたフィールド | `migrateTask()` が読み込み時に既定値を補う |
| 案件の並び順 | `projectOrder` は未登録案件を自動で末尾に置く |

**Bot が正しく作る必要があるのは実質3つ**：

1. **同一案件内のフィールド一致** — `projectName` / `projectNameInternal` / `companyName` / `customerContact`
2. **`hours` は分単位の数値**、0以下のステップは作らない
3. **`stepTypeId`** — `stepTypeMaster` の ID。無いと回数採番（白色→色付**2**）・納品名サフィックス・有料/無料判定が効かず**請求と売上の集計に影響する**。回数採番は「同じ `deliveryBase` が視点内で何番目か」を数えるだけ（`resolveViewpointSteps()` 相当・約20行）

## 12. 認証：Worker から Firestore を読み書きする

### 案 B-1（推奨）: Bot 専用 Google アカウント

1. Bot用Googleアカウントを用意（例 `koutei-bot@gmail.com`）
2. Firebase Authentication に**メール/パスワード**プロバイダを追加し登録
3. **確認メールを1回通して `email_verified: true` にする** ← 最大の落とし穴
4. アプリの「メンバー管理」から `allowedEmails` に追加
5. Worker から `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key={API_KEY}` → `idToken`（有効1時間）。KV にキャッシュ（既存 `COUNTER` namespace 流用可）

**長所**: 実装が fetch だけ。権限がワークスペース内に閉じる
**短所**: パスワードを Worker シークレットに置く

### 案 B-2（フォールバック）: サービスアカウント

Web Crypto で RS256 の JWT を自己署名 → OAuth2 トークン → Firestore REST。**ルールを完全にバイパス**するので `email_verified` 問題は起きないが、鍵が漏れるとDB全体を触られる。

> どちらも `firebase-admin`（Node依存）は Workers で動かない。REST を直接叩く。

### 12.1 Firestore REST の要注意点

**このプロジェクトのデータベースIDは `default`（`(default)` ではない）。** 間違えると404。

```
ベース: https://firestore.googleapis.com/v1/projects/koutei-zu/databases/default/documents
```

| 操作 | エンドポイント |
|---|---|
| マスタ1件読む | `GET {base}/workspaces/liebe-asia-team/data/stepTypeMaster` → `fields.value.stringValue` を `JSON.parse` |
| スナップショット読む | `GET {base}/workspaces/liebe-asia-team/data/botSnapshot` |
| 未完了タスクを絞る | `POST {base}/workspaces/liebe-asia-team:runQuery`（`structuredQuery` で `status == "pending"`） |
| タスク一括書き込み | `POST {base}:commit`（`writes` 配列。1案件ぶんを原子的に） |

- 値は**型付きJSON**（`{"stringValue":"A棟"}` / `{"integerValue":"480"}` / `{"nullValue":null}` / `{"booleanValue":false}`）。相互変換ヘルパーを Worker に置く
- `data/*` は「JSON文字列を `value` フィールドに入れる」二重構造。`tasks/*` は素のフィールド
