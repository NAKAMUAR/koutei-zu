# チャット連携（外部AIエージェント）設計

作成: 2026-07-27 / 版: 2.0 / 状態: **設計のみ（未実装）**

Telegram + Cloudflare Worker + Gemini の自作エージェントと工程図アプリを双方向に連携させる設計。

```
① チャット（案件登録 / 状況確認）
      ↓
② 工程図（Firestore への書き込み / 読み取り）
      ↓
③ 結果をチャットへ返答
```

**利用者は オーナー（kei.n412@gmail.com）本人のみ**を前提とする。

---

## 0. 結論

| 経路 | 実現性 | 方式 |
|---|---|---|
| **読み取り（生データ）** — 案件一覧・進捗・納期・担当者 | ◎ すぐ可能 | Worker から Firestore REST で直接読む |
| **読み取り（予定）** — いつ終わる・今日の予定・遅延 | △ 一手間要る | アプリがスケジュール結果のスナップショットを書き出す（第4章） |
| **書き込み** — 案件登録 | ○ 可能 | Worker から `tasks` へ直接 upsert。Telegram 側で確認を必須にする |

> **版1.0からの方針変更**: 版1.0では「受信箱（intake）方式」を推奨していたが、これは**アプリを開くまで登録が反映されない**ため ③ の即時返答が成立しない。要件（本人のみ・即時返答）を踏まえ、**Worker からの直接書き込み**に変更する。リスクは当初の見立てより低い（理由は 3.1）。

## 1. 現状の前提（調査結果）

### 1.1 データ構造 — 「1タスク = 1ステップ」

```
案件（projectName）
 └ 視点（viewpointName + assignee）
     └ ステップ（stepName）  ← これが Firestore の 1ドキュメント
```

- 保存先: `workspaces/liebe-asia-team/tasks/{taskId}`（`src/firebase.js` の `tasksStore`）
- 「案件を1件登録」＝ **複数ドキュメントを整合性を保って作る**こと

### 1.2 マスタ（`workspaces/{wid}/data/{key}`、値は JSON 文字列の `value` フィールド）

| キー | 用途 |
|---|---|
| `customerMaster` | 会社名・お客様担当者・契約形態（`offshore`/ラボ）・売上区分 |
| `employeeMaster` | 担当者名 |
| `stepTypeMaster` | ステップ種類（ID・ラベル・回数採番・納品名ベース・有料/無料） |
| `settings` | 稼働時間・休日・会社表示順 |

Bot は入力の自然文を**これらのマスタ値へ正規化**してから書く必要がある（表記ゆれで別会社・別担当者として登録されるため）。

### 1.3 認証・Firestore ルール（`firestore.rules`）

```
allow read, write: if request.auth != null
  && request.auth.token.email_verified == true
  && (オーナー or data/allowedEmails の emails 配列に含まれる)
```

**匿名認証では読み書きできない。** Bot にもメール確認済みの許可アカウントが要る（第5章）。

> 参考: `sync/Code.gs`（シート同期）は匿名認証で旧キー `data/tasks` に書いており、**現ルール・現構造では機能していないはず**（`docs/06_未実装機能設計書.md` 第11項で既出）。同じ轍を踏まないこと。

## 2. 読み取り（① → ② → ③）

### 2.1 質問の種類と必要なデータ

| 質問例 | 必要なもの | Worker から直接読めるか |
|---|---|---|
| 「今どんな案件がある？」 | `tasks` | ✅ |
| 「A棟の進捗は？」 | `tasks`（`completedHours` / `hours`） | ✅ |
| 「今週納期の案件は？」 | `tasks`（`deadline` / `projectDeadline`） | ✅ |
| 「ヤマダの残作業は？」 | `tasks`（`hours` 合計） | ✅ |
| **「A棟はいつ終わる？」** | `scheduleTasks()` の出力 | ❌ |
| **「今日は誰が何をやってる？」** | 同上 | ❌ |
| **「納期に間に合わない案件は？」** | 同上（`computeLateRisks`） | ❌ |

**分岐点はここ。** 予定日時は生データに入っておらず、`src/lib/schedule.js`（898行）が稼働時間・休日・欠勤・案件順から毎回計算している。Worker はこれを持っていない。

### 2.2 予定を返せるようにする2案

#### 案 R1: スナップショット方式 ★推奨

アプリが `scheduled` を計算するたび、**要約を1ドキュメントに書き出す**。Worker はそれを1回読むだけ。

```
アプリ（開いている間）
  scheduled = scheduleTasks(...)   ← 既存の useMemo
      ↓ デバウンス（30〜60秒・内容が変わった時のみ）
  data/botSnapshot   ← 要約 JSON
      ↓
Worker が1ドキュメント読んで回答
```

- **長所**: アプリ側 ~50行。Worker 側は JSON を読むだけ。Firestore 読み取りも1回で済む
- **短所**: **アプリを閉じている間は古くなる** → `generatedAt` を必ず含め、返答に「（10:32時点）」と明記する
- Bot 経由で案件を登録したら `staleSince` を立て、「スケジュール再計算はアプリを開いたときに反映されます」と添える

スナップショットの中身（案）:

```jsonc
{
  "generatedAt": 1753600000000,
  "staleSince": null,
  "projects": [
    {
      "projectName": "A棟", "companyName": "TAMAZEN",
      "projectDeadline": "2026-08-05",
      "endsAt": "2026-08-04T17:00",       // 案件全体の終了予定
      "lateRisk": false,
      "viewpoints": [
        { "viewpointName": "EX1", "assignee": "ヤマダ",
          "hours": 720, "completedHours": 240,
          "start": "2026-07-28T09:00", "end": "2026-07-30T15:00",
          "deadline": null }
      ]
    }
  ],
  "today": [
    { "assignee": "ヤマダ", "projectName": "A棟", "viewpointName": "EX1",
      "stepName": "白色", "from": "09:00", "to": "17:00" }
  ]
}
```

#### 案 R2: スケジューラを Worker に同梱

`src/lib/schedule.js` + `src/lib/utils.js` + `src/viewpoint/viewpointUtils.js`（計 約1,590行）は**npm 依存ゼロの純粋 ESM**。esbuild で1ファイルにバンドルすれば Worker にそのまま載る。

- **長所**: アプリが閉じていても常に正確
- **短所**: Worker のビルド手順が必要（現状は「Edit code に貼って Deploy」の運用）。アプリ側のロジック変更時に貼り直しが要り、**古いスケジューラで誤った予定を答える**リスクが残る

**R1 で始め、不足を感じたら R2 を検討する**のが妥当。

## 3. 書き込み（案件登録）

### 3.1 Worker から直接書いてよい理由

版1.0で「危険」とした不変条件のうち、大半は**アプリの読み込み時に自己修復される**：

| 不変条件 | 実態 |
|---|---|
| `priority` の会社別 1..n 採番 | `normalizePriorities()` が**購読のたび**に全件を振り直す。Bot は `priority: 99`（＝末尾）で書けばよい |
| 欠けたフィールド | `migrateTask()` が読み込み時に既定値を補う |
| 案件の並び順 | `projectOrder` は未登録案件を自動で末尾に置く |

**Bot が正しく作る必要があるのは実質この3つだけ**：

1. **同一案件内のフィールド一致** — `projectName` / `projectNameInternal` / `companyName` / `customerContact` が1文字でも違うと案件が分裂する（1回の登録で Bot が同じ値を使えばよい）
2. **`hours` は分単位の数値**、かつ **0以下のステップは作らない**（アプリ側も0のステップは登録しない仕様）
3. **`stepTypeId`** — `stepTypeMaster` の ID。これが無いと回数採番（白色→色付**2**）・納品名サフィックス・有料/無料判定が効かず、**請求と売上の集計に影響する**

3 は `stepTypeMaster` を読んで解決する。回数採番のロジックは「同じ `deliveryBase` が視点内で何番目か」を数えるだけ（`resolveViewpointSteps()` 相当、約20行）。

### 3.2 Bot が書くタスクドキュメント

1ステップ = 1ドキュメント。`workspaces/{wid}/tasks/{id}` に `:commit` で**まとめて原子的に**書く。

```jsonc
{
  "id": "task-1753600000000-0-a1b2c",   // task-{ms}-{連番}-{ランダム5桁}
  "projectName": "A棟",
  "projectNameInternal": "",
  "companyName": "TAMAZEN",             // customerMaster と完全一致
  "customerContact": "",
  "viewpointName": "EX1",
  "viewpointNameExternal": "",
  "viewpointCategory": "",
  "stepName": "白色",                    // stepTypeMaster から解決したラベル
  "stepOrder": 0,                        // 視点内 0 始まり
  "stepTypeId": "white",
  "stepDeliverySuffix": "",              // 回数採番の結果
  "assignee": "ヤマダ",                   // employeeMaster と完全一致
  "priority": 99,                        // 末尾。アプリが会社内で振り直す
  "hours": 480,                          // 分。8時間 = 480
  "completedHours": 0,
  "memo": "",
  "tentative": false, "tentativeStart": null, "tentativeEnd": null,
  "deadline": null,                      // 視点個別の納期
  "projectDeadline": "2026-08-05",       // 案件全体の納期
  "projectRequestDate": "2026-07-27",
  "manualStart": null, "manualEnd": null,
  "status": "pending",
  "completedAt": null,
  "createdAt": 1753600000000,            // 視点内でステップ順に +1 する
  "registeredDate": "2026-07-27",
  "stepAmount": "",                      // ラボ案件・無料ステップは空。オフショアのみ金額
  "stepRequestDate": "2026-07-27",
  "stepCompletedDate": "",
  "stepDeliveryNameOverride": "",
  "stepRoundType": "", "stepOutInHouse": "", "stepOutExternal": "", "stepOutVND": "",
  "externalId": "tg::{messageId}",       // 重複登録防止・/取消 の目印
  "createdVia": "telegram"               // Bot 作成の目印（アプリ側でバッジ表示に使える）
}
```

> **このフィールド表が Bot とアプリの契約になる。** アプリ側で `buildRecords`（`src/App.jsx`）のスキーマを変えたら、この章も Worker も更新すること。

### 3.3 誤登録への備え

即時に本番データへ書くので、次の3つを必須にする。

1. **Telegram での確認を必須**（`/確認` するまで書かない）— Gemini の読み違えを弾く最後の砦
2. **`/取消`** — 直前の `externalId` を引いて削除（KV に `lastExternalId` を保存）
3. **`createdVia: "telegram"`** — アプリ側で「Bot 登録」バッジを出し、目視確認できるようにする（任意・軽い）

## 5. 認証：Worker から Firestore を読み書きする

### 案 B-1（推奨）: Bot 専用 Google アカウント

1. Bot 用 Google アカウントを1つ用意（例 `koutei-bot@gmail.com`）
2. Firebase Authentication に**メール/パスワード**プロバイダを追加し、そのアカウントを登録
3. **確認メールを1回通して `email_verified: true` にする** ← 現ルールの必須条件。**最大の落とし穴**
4. アプリの「メンバー管理」から `allowedEmails` に追加
5. Worker から REST:
   - `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key={API_KEY}` → `idToken`（有効1時間）
   - `idToken` を KV にキャッシュして使い回す（既存の `COUNTER` namespace を流用可）

**長所**: 実装が fetch だけ。権限がワークスペース内に閉じる
**短所**: パスワードを Worker シークレットに置く

### 案 B-2（フォールバック）: サービスアカウント

Web Crypto で RS256 の JWT を自己署名 → OAuth2 トークン → Firestore REST。**ルールを完全にバイパス**するので `email_verified` 問題は起きないが、鍵が漏れると DB 全体を触られる。B-1 が詰まった場合の代替。

> どちらも `firebase-admin`（Node 依存）は Workers で動かない。REST を直接叩く。

### 5.1 Firestore REST の要注意点

**このプロジェクトのデータベース ID は `default`（`(default)` ではない）。** パスを間違えると 404 になる。

```
ベース: https://firestore.googleapis.com/v1/projects/koutei-zu/databases/default/documents
```

| 操作 | エンドポイント |
|---|---|
| マスタ1件読む | `GET {base}/workspaces/liebe-asia-team/data/stepTypeMaster` → `fields.value.stringValue` を `JSON.parse` |
| スナップショット読む | `GET {base}/workspaces/liebe-asia-team/data/botSnapshot` |
| 未完了タスクを絞って読む | `POST {base}/workspaces/liebe-asia-team:runQuery`（`structuredQuery` で `status == "pending"`） |
| タスク一括書き込み | `POST {base}:commit`（`writes` 配列。**1案件ぶんを原子的に**） |

- 値は**型付き JSON**（`{"stringValue":"A棟"}` / `{"integerValue":"480"}` / `{"nullValue":null}` / `{"booleanValue":false}`）。プレーン JSON ↔ 型付き JSON の相互変換ヘルパーを Worker に置くこと
- `data/*` の値は「JSON文字列を `value` フィールドに入れる」二重構造。`tasks/*` は素のフィールド

## 6. Worker 側の実装タスク（`k04nakamura/agent`。このリポジトリ外）

| # | 内容 |
|---|---|
| 1 | Firestore REST クライアント（型付きJSON変換・`idToken` の KV キャッシュ） |
| 2 | マスタ取得（`customerMaster` / `employeeMaster` / `stepTypeMaster`）＋ 5分程度の KV キャッシュ |
| 3 | 意図判定: 登録 / 状況確認 / その他 を Gemini で振り分け（`/案件` `/状況` の明示コマンドも受ける） |
| 4 | **登録**: Gemini の `responseSchema` で構造化出力 → マスタ照合 → 確認プレビュー返信 → `/確認` で `:commit` |
| 5 | **確認**: `botSnapshot` ＋ `tasks` を読んで Gemini に要約させて返信（`generatedAt` を明記） |
| 6 | `/取消`: KV の `lastExternalId` からタスクを引いて削除 |
| 7 | エラー処理: マスタに無い会社名・担当者は**勝手に作らず**候補を提示して聞き返す |

### コマンド設計（案）

```
/案件 TAMAZEN A棟 外観1 白8h 色付4h 担当ヤマダ 納期8/5
→ 【登録内容の確認】
   会社: TAMAZEN / 案件: A棟
   依頼日: 2026-07-27 / 納期: 2026-08-05
   ─ EX1（担当: ヤマダ）
      白色  8:00
      色付  4:00
   合計 12:00 ／ 登録は /確認、破棄は /取消

/状況              全案件のサマリ
/状況 A棟          特定案件の進捗と終了予定
/今日              今日の予定（担当者別）
/納期              納期が近い順
/取消              直前の登録を取り消し
```

自由文（「A棟どうなってる？」）も 3 の意図判定で同じ処理に流す。

## 8. セキュリティ

| 項目 | 対応 |
|---|---|
| 発信者の制限 | `MY_CHAT_ID` 一致チェック（既存）。**本人のみなのでこれが実質の認可** |
| Webhook 検証 | `WEBHOOK_SECRET`（既存） |
| 認証情報 | Bot のパスワード／鍵は Worker シークレットのみ。**GitHub 公開リポジトリに絶対入れない** |
| 権限の最小化 | 案 B-1（メンバー権限）を優先。B-2 は全 DB を触れる |
| **案件情報が Gemini API を通る** | 会社名・案件名・担当者が外部 API へ送られる。読み取り要約でも同様。**業務上の判断が必要** |
| 誤登録 | `/確認` 必須 ＋ `/取消` ＋ `createdVia` バッジ（3.3） |
| 監査 | タスクに `externalId` / `createdVia` を残す |

> 引き継ぎメモの「Vercel 公開ページの Firebase 認証」は**別問題**。工程図は Firestore ルールで守られており、Bot が公開ページに案件データを出力しない限り影響しない。**Bot が生成する Vercel ページに工程図のデータを載せないこと。**
