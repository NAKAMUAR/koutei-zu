## 1. はじめに

### 1.1 本書の目的

本書は「工程図（koutei-zu）」が満たすべき業務上・機能上・非機能上の要件を定義することを目的とする。建築CG（パース・写真合成等）制作チームの日々の制作スケジュールを、案件・視点（依頼項目）・工程ステップの単位で管理し、担当者ごとの稼働を自動でタイムライン化すること、およびそこから売上・帳票までを一続きで扱えるようにすることを狙いとする。

### 1.2 用語定義

| 用語 | 定義 |
|---|---|
| 案件（プロジェクト） | お客様から受注した制作の単位。社外案件名・社内案件名（案件コード）を持つ。 |
| 視点（依頼項目） | 案件内の制作対象の単位。例：「外観視点①」「内観視点①_パターンA」。担当者は視点ごとに割り当てる。 |
| ステップ（工程） | 視点内の作業工程。例：「ホワイト」「カラー」「カラー修正（無料）」。各ステップが制作時間を持つ。 |
| タスク | 「1案件 × 1視点 × 1ステップ」で確定する管理上の最小単位。1タスク=1Firestoreドキュメント。 |
| ステップ種類（stepTypeId） | ステップの分類。マスタ（ステップ設定）で管理し、有料/無料・納品名の基礎・連番有無を持つ。 |
| ラウンド種類（stepRoundType） | ステップが「初回（initial）／追加（add）／修正（fix）」のどれかを表す区分。売上・修正集計の基準。 |
| 制作時間（hours） | そのステップの見積もり作業時間（h）。スケジュール枠の長さの基準。 |
| 完了時間（completedHours） | そのステップで既に完了した作業時間（h）。 |
| 開始時間指定（manualStart） | 自動スケジュールより優先してタスクの着手時刻を固定する指定。 |
| 終了時間指定（manualEnd） | 作業終了予定時刻の固定指定。エンジニアの作業完了見込み時刻。 |
| 実終了時刻（actualEnd） | 完了時に記録する実際の終了時刻。後続タスクの着手下限（doneFloor）になる。 |
| 納期（deadline） | お客様へ提出する期限日。視点ごとに設定する。案件全体の納期（projectDeadline）も別に持てる。 |
| 残業 | 担当者・期間・時間帯を指定して通常稼働枠に追加する稼働時間。 |
| 欠勤（休日・不在） | 担当者の対応不可日・時間帯。終日または時間帯で指定する。 |
| 祝日 | チーム全体の非稼働日。ベトナムの祝日を含め、マスタ画面で登録する。 |
| 差し込み | 開始時間を指定したタスクが時間枠を先取りし、指定なしのタスクが前後の空きへ分割して入ること。 |
| 確認待ち | 視点/案件を完了した直後に入る中間状態。お客様確認の結果で「完了」または「進行中へ戻す」を選ぶ。 |
| 制作中断（suspended） | 納品後の確認待ちなどで進行できない案件を、一旦スケジュールから外した状態。再開できる。 |
| 中止（cancelled） | 案件が取りやめになった状態。実績は残すが後続スケジュールには影響させない。 |

### 1.3 対象範囲

- **対象**
  - 制作チームの社内スケジュール管理（案件登録・進捗・カレンダー可視化・連絡文生成）
  - 売上登録表の作成・集計（外注費・請求/入金チェックを含む）
  - 帳票の作成・印刷（見積書・発注書・請求書）
  - 案件整理表（案件の一覧管理）、会社別の集計
  - タスクメモ（アプリを開いている間の時刻通知つきメモ）
  - スプレッドシート（Google Apps Script）からの案件取り込み
- **対象外**
  - 会計ソフト連携・入金消込の自動化
  - 外部顧客向けの公開機能（お客様が直接ログインする画面）
  - LINE等の外部メッセージ自動連携（将来検討）
  - アプリを閉じている間のプッシュ通知

## 2. 業務要件

### 2.1 現状と課題

- 建築CG制作は「案件 → 視点 → 工程」の階層を持ち、担当者・納期が絡むため、手作業のスケジュール調整が煩雑。
- 担当者ごとの稼働がいつ空くか、案件がいつ終わるかを即座に把握したい。
- 進捗（完了時間）に応じて終了見込みが変動するため、常に最新の予定を全員で共有したい。
- 制作情報と売上・請求情報が別管理になっており、同じ内容を二重入力していた。

### 2.2 業務フロー（あるべき姿）

1. 受注した案件を、視点・ステップ・制作時間とともに登録する（仮案件としての先行登録も可）。スプレッドシートからの自動取り込みも使える。
2. 担当者・開始/終了/納期を設定すると、システムが自動でタイムラインを生成する（並び順の既定は「同じ会社の中で納期の早い順」）。
3. 日々の進捗（完了時間）を入力すると、残作業に応じて終了見込みが自動で調整される。
4. カレンダー・担当者別・サマリーで状況を共有し、会社別の業務連絡文を生成して送付する。
5. 完了した視点・案件は終了時刻（実績）を記録して「確認待ち」へ移し、確認が済んだら完了タブへ移動する。
6. ステップに金額を入れると売上登録表へ自動で行が起こり、そこから月次集計・請求/入金チェックができる。
7. 必要に応じて見積書・発注書・請求書を作成・印刷する。

### 2.3 利用者（アクター）

| アクター | 説明 |
|---|---|
| オーナー | `src/firebase.js` の `OWNER_EMAILS` とFirestoreルールに直書きされた管理者。メンバー許可リストを編集できる。 |
| 制作管理者 | 案件登録・スケジュール調整・売上/帳票作成・連絡文送付を行う中心利用者。 |
| 制作担当者（エンジニア） | 自分の担当タスクの進捗入力・確認を行う。 |

※ 認証はGoogleアカウント（Gmail）のみ。オーナー、または `data/allowedEmails` に登録されたメンバーだけが読み書きできる。同一ワークスペースIDの利用者でデータを共有する小規模チーム運用を前提とする。

### 3.2 主要機能の詳細要件

#### F-02 新規タスク登録
- 案件は「社外案件名」を必須とする。社内案件名・会社名・お客様担当者は任意。
- 1案件に複数の視点を登録でき、各視点は複数のステップ（種類＋名称＋制作時間＋完了時間）を持つ。
- 視点ごとに担当者・開始/終了時間・納期を上書き設定できる（未設定時はデフォルト担当者を適用）。
- 制作時間0でも登録可（先行枠取り）。完了時間≧制作時間のステップは登録時点で完了扱い。
- 「仮案件」フラグでスケジュール枠は確保しつつ仮予定として区別表示できる。
- ステップには請求・売上用の情報（ステップ種類・金額・依頼日・納品名・外注先・外注費VND）も持たせられる。

#### F-05 / F-06 自動スケジューリングと指定
- 営業時間は午前（既定8:00–12:00）＋午後（既定13:00–17:00）、土日除外、第2・第4土曜は午前のみ、登録された祝日は終日非稼働。
- 作業順は「案件の並び順 → 案件内の並び順（priority） → ホワイト工程を全視点優先 → 登録順」。
- **優先順位を人が採番する運用は廃止**。新規案件の既定の並び順は「同じ会社の中で納期（実効）の早い順」に自動で挿入される（`deadlineInsertPriority`）。並びは後からドラッグ・↑↓で手動変更できる。
- 開始時間を指定したタスクは事前に枠を予約（差し込み）。指定なしタスクは前後の空きへ分割。
- 終了時間指定は「その時刻で打ち切り、後続タスクはその時刻以降に開始」。

#### F-07 納期超過警告
- 納期は視点ごとに日付で設定。登録/更新時に実スケジュールを試算し、視点の終了予定日が納期日を超える場合は確認モーダルと入力フォームのプレビューに警告を表示する。
- 案件ヘッダー・視点カードに納期バッジを表示し、超過時は赤系で警告表示する。
- 案件の納期表示は「視点ごとの納期のうち最も早いもの」を用いる。案件全体の納期（projectDeadline）を別に設定することもできる。

#### F-08 進捗連動の終了予定調整（重要要件・**旧版から仕様変更**）
- スケジュール用の所要時間は **「残作業＝制作時間 − 完了時間」のみ**で決まる。
- **経過時間では終了予定を膨張させない**。完了時間を入力しないまま時間が経っても、枠は伸びない。0.5hのタスクは常に0.5h枠で、開始予定どおりに表示される。
- 例：4hのタスクで完了2hを入力 → 残り2h分の枠になる。完了1h → 残り3h分の枠になる（開始位置は動かない）。
- 遅れが後続へ伝わるのは「完了時に実終了時刻（actualEnd）を入力したとき」だけ。その時刻が後続タスクの着手下限（doneFloor）になる。
- 画面は1分ごとに再計算し、後続タスクの開始も追従する。

> 旧版（1.0）には「開始〜現在の経過稼働時間 ＋ 残作業時間で枠を取り直す（完了1h→14:00へ後ろ倒し）」と書かれていたが、これは**実装と逆**であり誤り。現在の実装は上記のとおり「残作業のみ」。

#### F-09 残業／F-10 欠勤／F-24 祝日
- 残業：担当者・期間（開始日〜終了日）・時間帯を指定し、通常稼働枠にマージしてスケジュール・カレンダーへ反映。
- 欠勤：終日または時間帯で対応不可を指定。該当時間はスケジュールから除外し、カレンダーにグレー表示。
- 祝日：チーム全員が休みになる日。ベトナムの祝日は年を選ぶと候補が提示され、まとめて登録できる（旧暦ベースの日付は目安のため要確認）。任意の臨時休業日も手動登録できる。

#### F-13 / F-25 完了・確認待ち
- 視点完了／案件完了では実終了時刻を入力し、まず **「確認待ち」** に入る（完了タブへは行かない）。
- 確認待ちでは追加修正メモを記入でき、記入すると期限がリセットされる。3日更新がないとグレー表示、7日で自動的に完了タブへ移る。
- 「進行中へ戻す」でスケジュールへ復帰できる。
- 中止（cancelled）は実績を残したままスケジュールから外す。中断（suspended）は再開できる一時停止。

#### F-14 終了超過ポップアップ
- 視点単位で終了予定を過ぎると表示。対応は以下4種。
  - ① 視点完了（実終了時刻を入力 → 確認待ちへ）
  - ② 追加修正（その視点に追加ステップを足す）
  - ③ 遅延（新しい終了予定へ更新し、差分の稼働時間を加算・遅延履歴を記録）
  - ④ 後で（30分スヌーズ）

#### F-30 / F-31 売上登録表と自動同期
- 売上は「1か月＝1ドキュメント」で管理する（`data/sales_{YYYY-MM}`）。
- ステップに金額（制作金額 or 外注金額VND）を入れると、1ステップ＝1行で売上行が自動生成される。行は `srcRound = step:{taskId}` で識別し、手動で足した行（src なし）には一切触れない。
- 自動生成行のうち、会社・担当・案件名・制作種類・納品名・金額・外注先・依頼日は毎回上書きされる。区分・納品日・請求/入金日・備考・枚数などユーザーが編集する項目は保持される。
- ステップから金額を消すと、対応する自動生成行も消える。
- 売上区分は、お客様マスタの契約形態（オフショア/ラボ）と売上区分（国内/国際）から `offshore_dom / offshore_intl / lab_dom / lab_intl` の4種で自動判定する。

#### F-36 スプレッドシート連携
- スタッフが書く「Project Schedule」の『product schedule』タブ →（自動転記・自動判定）→「工程図連携」シート →（人が補正）→ 工程図、の2段階。
- 取り込んだタスクは `externalId`（`案件コード::視点名::n回目::ステップ種類`）を持ち、アプリ側で削除すると `data/deletedExternalIds` に記録されて再送信しても復活しない。
- 詳細な手順・仕様は `docs/08_スプレッドシート連携.md` を参照。

## 4. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 数百件規模のタスクで、編集・スケジュール再計算が体感即時であること。 |
| 可用性 | GitHub Pages＋Firebaseのマネージドサービスに依存。SLAはサービス標準に準拠。 |
| 同時編集 | 1タスク=1ドキュメントの差分書き込みで、複数端末同時編集でも表示が乖離しないこと。 |
| リアルタイム性 | Firestoreの購読で、他端末の変更が即時に画面反映されること。 |
| セキュリティ | 認証必須。Firestoreルールでオーナー＋許可メンバー（email_verified）のみ読み書き可。 |
| 対応端末 | PC／タブレット／スマートフォン（レスポンシブ。ドラッグ操作はPC、↑↓ボタンはスマホ）。 |
| 国際化 | 日本語UI。日本のカレンダー慣習（土日・第2/4土曜）＋ベトナムの祝日に対応。 |
| 保守性 | 機能ごとにファイル分割（`src/views/`・`src/lib/`・`src/billing/`・`src/sales/` ほか）。1ファイル1800行（App.jsx のみ2600行）を上限とし、ESLintで機械的に強制する。 |
| UI設計品質 | ネイティブダイアログ禁止・段階的開示・モードレスなど10項目の設計原則を `docs/07_UI設計原則.md` で定め、主要項目をESLintで強制する。 |
| 初期表示 | 使用頻度の低いビューは `React.lazy` で遅延読み込みし、初回読み込みを軽くする。 |

## 5. 制約・前提条件

- フロントエンドのみのSPA。専用サーバを持たず、バックエンドはFirebase（Firestore＋Auth）。サーバレス関数は使っていない。
- TypeScript不使用（JavaScript/JSX）。スタイルはインラインスタイル。
- ホスティングはGitHub Pages。`npm run deploy`（vite build → gh-pages）で公開。ソース（main）への push とセットで運用する。
- ワークスペースIDで共有範囲を区切る単一テナント想定（マルチテナントの厳密分離は対象外）。
- 稼働時間（午前・午後のスロット）は**全員共通**。担当者ごとの時差設定は未対応（`docs/06` の項目10）。
- アプリを閉じている間の通知はできない（タスクメモの通知はブラウザを開いている間のみ）。
- Firestoreルールの変更は、Firebaseコンソールへの手動デプロイが必要。
