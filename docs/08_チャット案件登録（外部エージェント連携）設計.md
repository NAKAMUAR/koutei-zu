# チャット経由の案件登録（外部AIエージェント連携）設計

作成: 2026-07-27 / 状態: **設計のみ（未実装）**

Telegram + Cloudflare Worker + Gemini の自作エージェントから、工程図アプリへ案件を登録する仕組みの設計。
「必要なもの」を実装前に洗い出すためのドキュメント。

---

## 0. 結論

**実現可能。** ただし次の2点が設計上の分岐点になる。

1. **Bot から Firestore へ書く権限をどう取るか**（現ルールは「メール認証済みの許可メールアドレス」しか通さない）
2. **Bot が「タスクドキュメント」を直接作らないこと**（データ不変条件が多く、壊すと全画面に波及する）

推奨は **受信箱（intake）方式**：Bot は「登録リクエスト」を1件書くだけ。実際のタスク生成は**アプリ側の既存ロジック**（`buildRecords`）に任せる。

---

## 1. 現状の前提（調査結果）

### 1.1 データ構造 — 「1タスク = 1ステップ」

```
案件（projectName）
 └ 視点（viewpointName + assignee）
     └ ステップ（stepName）  ← これが Firestore の 1ドキュメント
```

- 保存先: `workspaces/liebe-asia-team/tasks/{taskId}`（`src/firebase.js` の `tasksStore`）
- 「案件を1件登録」＝ **複数ドキュメントを整合性を保って作る**こと。単純な1レコード追加ではない。

### 1.2 タスク1件に必要なフィールド（`src/App.jsx` `buildRecords` より）

| 分類 | フィールド | 備考 |
|---|---|---|
| 識別 | `id` | `task-{ms}-{seq}-{rand}` |
| 案件 | `projectName` / `projectNameInternal` / `companyName` / `customerContact` | 同一案件の全タスクで**完全一致**が必須（ズレると案件が分裂する） |
| 視点 | `viewpointName` / `viewpointNameExternal` / `viewpointCategory` | |
| ステップ | `stepName` / `stepOrder` / `stepTypeId` / `stepDeliverySuffix` | `stepTypeId` は `stepTypeMaster` の ID。`resolveViewpointSteps()` が回数付きラベル（例「色付2」）と納品名サフィックスを解決する |
| 稼働 | `assignee` / `hours` / `completedHours` | `hours` は分単位。`hours <= 0` のステップは**登録されない** |
| 並び | `priority` | **会社ごとに 1..n** で採番。`normalizePriorities()` が全件を振り直す |
| 期日 | `deadline`（視点個別）/ `projectDeadline`（案件全体）/ `projectRequestDate` | |
| 状態 | `status`（`pending`/`done`）/ `createdAt` / `completedAt` / `registeredDate` | |
| 請求 | `stepAmount` / `stepRequestDate` / `stepCompletedDate` / `stepRoundType` / `stepOut*` | 金額はお客様マスタの `contractType === 'offshore'` の会社のみ。ラボ案件は空固定 |
| 外部 | `externalId` | 外部取り込みの重複防止キー（既存のシート同期で使用中） |

> **重要**: これらの導出ロジック（ステップ回数の採番、優先順位の会社別採番、無料ステップの金額除外、登録日の自動補完など）は App.jsx 側にしか無い。Worker 側に再実装すると必ず二重管理になり、仕様変更のたびに壊れる。

### 1.3 認証・Firestore ルール（`firestore.rules`）

```
allow read, write: if request.auth != null
  && request.auth.token.email_verified == true
  && (オーナー or data/allowedEmails の emails 配列に含まれる)
```

つまり **匿名認証では書けない**。Bot にも「メール確認済みの許可アカウント」が要る。

> 参考: `sync/Code.gs`（スプレッドシート同期）は匿名サインインで旧キー `data/tasks` に書いており、**現ルール・現データ構造では機能していないはず**（`docs/06_未実装機能設計書.md` 第11項で既出）。今回の実装で同じ轍を踏まないこと。

### 1.4 参照するマスタ（`data/` コレクション）

| キー | 用途 |
|---|---|
| `customerMaster` | 会社名・お客様担当者・契約形態（offshore/lab）・売上区分 |
| `employeeMaster` | 担当者名 |
| `stepTypeMaster` | ステップ種類（ID・ラベル・回数採番・納品名ベース・有料/無料） |
| `settings` | 稼働時間・会社表示順など |

Bot が受け取った自然言語を**これらのマスタ値へ正規化**できないと、表記ゆれで別会社・別担当者として登録されてしまう。

## 2. 方式比較

| 方式 | 内容 | 評価 |
|---|---|---|
| **A. Bot が tasks を直接書く** | Worker が Gemini の出力からタスクドキュメント群を生成し Firestore へ upsert | ❌ 非推奨。1.2 の不変条件を Worker 側に再実装することになり、優先順位の採番ズレ・案件分裂・請求への誤連携を招く |
| **B. 受信箱（intake）方式** ★推奨 | Worker は「登録リクエスト1件」を `data/intake_{id}` に書く。アプリが取り込みUIで確認 → 既存 `buildRecords` でタスク化 | ✅ 業務ロジックがアプリ1か所に閉じる。誤登録も取り込み前に握り潰せる |
| **C. Cloud Functions を挟む** | サーバ側で共通ロジックを実行 | △ 一番きれいだが Firebase Functions（Blaze プラン）と CI/CD の新設が必要。現構成にはオーバーキル |

**推奨は B。** 将来 C に寄せたくなっても、intake のデータ契約はそのまま使い回せる。

## 3. 推奨アーキテクチャ（受信箱方式）

```
Telegram
  │  「/案件 TAMAZEN A棟 外観1 白8h 色付4h 担当ヤマダ 納期8/5」
  ▼
Cloudflare Worker (telegram-agent)
  │ 1. MY_CHAT_ID で発信者チェック
  │ 2. Firestore からマスタ取得（customerMaster / employeeMaster / stepTypeMaster）
  │ 3. Gemini に「マスタの候補リスト付き」で構造化 JSON を生成させる（responseSchema 使用）
  │ 4. Telegram に確認メッセージを返す（登録内容のプレビュー ＋「はい/いいえ」）
  │ 5. 承認されたら Firestore の data/intake_{id} に1件書き込み
  ▼
Firestore  workspaces/liebe-asia-team/data/intake_{id}
  ▼
工程図アプリ（新タブ「取り込み」）
  │ 未処理の intake を一覧表示 → 内容確認・修正 → 「登録」
  │ 内部的には setForm(payload) → 既存の保存処理を通す
  ▼
tasks サブコレクション（＝通常登録と完全に同じ結果）
```

### なぜ「確認ステップ」を2回入れるか
- Telegram 側の確認 = Gemini の読み違え（会社名・時間）を弾く
- アプリ側の取り込み = 優先順位・担当者・納期の最終判断（人がやるべき業務判断）

慣れてきたら「信頼度が高い intake は自動取り込み」に緩める余地は残る。

## 4. データ契約（intake ペイロード）

**アプリの `form` オブジェクトと同じ形にする。** こうすると取り込み処理が `setForm(payload)` + 既存保存で済み、バリデーションも100%再利用できる。

```jsonc
{
  "source": "telegram",
  "createdAt": 1753600000000,
  "chatId": "8991512381",
  "rawText": "TAMAZEN A棟 外観1 白8h 色付4h 担当ヤマダ 納期8/5",  // 監査用の原文
  "status": "pending",            // pending | applied | rejected
  "externalId": "tg::{messageId}", // 重複取り込み防止
  "confidence": { "companyName": "high", "assignee": "low" }, // 任意：低いものはUIで警告表示
  "form": {
    "projectName": "A棟",
    "projectNameInternal": "",
    "companyName": "TAMAZEN",          // customerMaster の値と完全一致
    "customerContact": "",
    "assignee": "ヤマダ",               // employeeMaster の値と完全一致
    "priority": "",                     // 空 = 末尾に自動採番
    "memo": "",
    "projectRequestDate": "2026-07-27", // YYYY-MM-DD
    "projectDeadline": "2026-08-05",
    "tentative": false,
    "tentativeStart": "", "tentativeEnd": "",
    "viewpoints": [
      {
        "viewpointName": "EX1",
        "viewpointNameExternal": "",
        "viewpointCategory": "",
        "assignee": "ヤマダ",
        "manualStart": "", "manualEnd": "",
        "deadline": "",
        "deliveryName": "",
        "steps": [
          { "stepTypeId": "white", "name": "白色", "hours": "8:00", "assignee": "", "amount": "" },
          { "stepTypeId": "color", "name": "色付", "hours": "4:00", "assignee": "", "amount": "" }
        ]
      }
    ]
  }
}
```

**注意点**
- `hours` は `"8:00"` / `"8"` の文字列（アプリの `parseHM()` が解釈する）。**0 や空のステップは登録されず消える**
- `stepTypeId` を必ず入れる。無いと回数採番（白色→色付2 など）と納品名サフィックスが効かない
- `priority` は空推奨。Bot が数字を決めると既存案件の順序を壊す
- `stepAmount` はラボ案件では無視される（アプリ側が空に固定する）

### 保存先
`workspaces/{wid}/data/intake_{id}` — 既存の `prefixStore()`（`src/firebase.js`）がそのまま使える（`billingStore` / `salesStore` と同じ仕組み）。**ルール変更なしで読み書きできる。**

## 5. 認証：Bot から Firestore へ書く方法

### 案 B-1（推奨）: Bot 専用 Google アカウント
1. Bot 用の Google アカウントを1つ用意（例 `koutei-bot@gmail.com`）
2. Firebase Authentication に**メール/パスワード**プロバイダを追加し、そのアカウントを登録
3. **確認メールを1回通して `email_verified: true` にする**（現ルールが必須にしている。ここが最大の落とし穴）
4. アプリの「メンバー管理」から `allowedEmails` に追加
5. Worker から REST 2発:
   - `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key={API_KEY}` → `idToken`
   - `PATCH https://firestore.googleapis.com/v1/projects/koutei-zu/databases/default/documents/workspaces/{wid}/data/intake_{id}` に `Authorization: Bearer {idToken}`
6. `idToken` は1時間有効。KV にキャッシュして使い回す（`refreshToken` で更新も可）

**長所**: 実装が fetch だけ。権限がワークスペース内に閉じる（漏洩時の被害が限定的）
**短所**: パスワードを Worker シークレットに置く。`email_verified` の手当てが要る

### 案 B-2（フォールバック）: サービスアカウント
Worker で Web Crypto を使い RS256 で JWT を自己署名 → OAuth2 アクセストークン → Firestore REST。
**Firestore ルールを完全にバイパスする**ので `email_verified` 問題は起きないが、秘密鍵が漏れると DB 全体を触られる。B-1 が詰まった場合の代替。

> どちらも `firebase-admin`（Node 依存）は Workers で動かない点に注意。REST を直接叩く。

### （任意）ルール強化
Bot の書き込み先を intake だけに限定したい場合は、`firestore.rules` に Bot の uid 判定を足して `data/intake_*` 以外への write を拒否する。**ルール変更は Firebase コンソールへの手動デプロイが必要**（`docs/06` 第1項）。

## 7. コマンド設計（Telegram 側）

```
/案件 TAMAZEN A棟 外観1 白8h 色付4h 担当ヤマダ 納期8/5
→ Bot:
  【登録内容の確認】
  会社: TAMAZEN
  案件: A棟
  依頼日: 2026-07-27 / 納期: 2026-08-05
  ─ EX1（担当: ヤマダ）
     白色  8:00
     色付  4:00
  合計: 12:00
  この内容で登録しますか？ → /確認 で登録 / /取消 で破棄
```

- 自然文でも受ける（`/案件` 以降は自由文 → Gemini が構造化）
- 画像（工程表のスクショ等）も既存の画像→CSV機能と同じ経路で構造化 → intake へ、という拡張も同じ設計に乗る
- **登録は必ず確認を挟む**（工程図は請求・売上に直結するため）

## 8. セキュリティ上の注意

| 項目 | 対応 |
|---|---|
| 発信者の制限 | `MY_CHAT_ID` 一致チェック（既存）。**社内で複数人が使うなら許可 chatId のリスト化が必要** |
| Webhook 検証 | `WEBHOOK_SECRET`（既存） |
| 認証情報の露出 | Bot のパスワード／サービスアカウント鍵は Worker シークレットのみ。**GitHub 公開リポジトリへ絶対に入れない** |
| 権限の最小化 | 案 B-1（メンバー権限）を優先。B-2 のサービスアカウントは全 DB を触れる |
| 案件データの外部流出 | Worker は intake 書き込み用に**マスタを読む**。案件情報が Gemini API へ送られる点は業務上の判断が必要（顧客名・案件名を含む） |
| 監査 | intake に `rawText` / `chatId` / `createdAt` を残す |

> 引き継ぎメモにあった「Vercel 公開ページの認証」は今回の案件登録とは**別問題**。工程図側は Firestore ルールで守られており、Bot 経由でも公開ページに案件データを出さない限り影響しない。
